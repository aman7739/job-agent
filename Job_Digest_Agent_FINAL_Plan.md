# Job Digest Agent: Final build plan: agent, private app, project site (22 sessions)

A personal agent that finds as many relevant fresher, internship and apprenticeship jobs as it can, from permitted sources only, and delivers one digest of apply links every morning at about 08:00 IST to Telegram and email. You apply manually. A private, password-protected web app lets you use it from any device, and a small public site presents the project properly. It is for you only: one profile, one login, no other users.

## Goals

- Find as many jobs as possible that fit you, then rank them so you read the best first.
- Deliver to both Telegram and email, with the email going to a different mailbox from your alerts inbox.
- Never apply for you, never scrape sites that forbid it, never claim a score is a hiring prediction.
- Stay usable from any device through a private hosted app.

## How to work each session

- A session is one focused 2 to 3 hour block. Build only that session, run its Check, commit, move on.
- If a session takes double the time, cut scope (fewer sources, fewer pages), never the tests.
- Keys and your real profile live in .env, GitHub secrets or the database, never in Git or prompts.
- Commit message style: 'day8: eligibility + match score'.
- Before using any source, API or host, re-check its current terms, limits and availability that day.

## Decisions

- Personal use only. No accounts for other people, no sign-up.
- Stack: Python 3.12, httpx, Pydantic (strict), PyYAML, SQLAlchemy + psycopg, Jinja2, FastAPI, pytest, GitHub Actions. No LLM in v1; the top-15 re-rank is an optional later extra.
- Database: Supabase Postgres, using the pooler connection string. The direct connection is IPv6-only and GitHub runners often lack IPv6. Verify in Session 1.
- Profile: profile.yaml is gitignored. Until Session 13 the scheduled run reads it from a repository secret (PROFILE_YAML); from Session 13 it lives in the database. Only profile.example.yaml is committed.
- Delivery: Telegram and email are both supported; channels are set in the profile. Jobs count as notified once at least one channel succeeds.
- Alerts mailbox vs notification mailbox: the agent reads mailbox A (your LinkedIn/Naukri alerts) over IMAP with an app password and sends the digest to mailbox B. IMAP is preferred because Google OAuth apps in testing mode reportedly issue refresh tokens that expire in about 7 days. Verify.
- Sources: public job-board APIs, official search APIs and your own email alerts. No scraping of LinkedIn, Naukri or Indeed, no browser automation, no auto-applying.
- Website: the public project site is static, generated by the same Python and Jinja2 code, with near-zero JavaScript. The private app is separate, noindex and behind login.

## Architecture

Scheduler (08:00 IST) -> fetch sources and email alerts -> normalize -> dedupe -> freshness filter -> eligibility + match score -> build digest (two sections) -> send Telegram and email -> mark notified once one channel succeeds -> save digest.

Parts: GitHub Actions runs the daily agent; Supabase Postgres holds jobs, history, status and (from Session 13) your profile; the private app reads and edits the same database; the public project site is static and shows no private data.

## Match score

| Factor | Weight |
|---|---|
| Skill overlap | 4 |
| Role match | 3 |
| Level fit | 2 |
| Location | 1 |
| Total | 10 |

The score is informational and is not a hiring prediction. Every job shows matched skills, missing skills, the location reason and the source. Strong matches are 7 and above; Maybe is 4 to 6. Salary or stipend is shown, or 'salary not listed'.

## Phase 1: the agent (Sessions 0 to 12)

### Session 0: Setup (~2h)

- Install Python 3.12, Git, VS Code. Create the GitHub repo, clone it, create and activate .venv.
- Add .gitignore (.venv, .env, profile.yaml, __pycache__), requirements.txt, pytest.
- Add ci.yml that runs pytest on push. Make the first commit, then stop for the day.

**Check:** A fresh clone + pip install -r requirements.txt + pytest is green.

---

### Session 1: Profile + schema (~3h)

- Use the final profile.yaml (version 3). Commit only profile.example.yaml.
- Strict Pydantic model: unknown keys rejected, required fields enforced, lists deduplicated on load.
- database/schema.sql: job_sources, jobs, seen_jobs (fingerprint primary key), digests, source_runs, email_messages (processed Message-IDs).
- Connect through db.py using the pooler connection string. Store the profile as the PROFILE_YAML repo secret for now.

**Check:** A typo'd key and a missing required field both fail with a clear message; the tables exist.

---

### Session 2: Source interface + Greenhouse and Lever (~3h)

- JobSource protocol: a name and an async fetch() returning a list of RawJob.
- sources.yaml with 20 to 30 verified company board slugs to start; adapters for the public Greenhouse and Lever JSON endpoints.
- Fetch sequentially with a small delay and a clear User-Agent. Filter location to India or remote after fetching.

**Check:** A script prints today's raw jobs; one bad slug logs a warning and the run continues.

---

### Session 3: Ashby, SmartRecruiters, Workable (~3h)

- Ashby: public posting API per board name; skip postings that are not listed.
- SmartRecruiters: public Postings API per company id (availability depends on the customer's plan).
- Workable: boards at apply.workable.com/<subdomain>; verify the endpoint and terms before relying on it.
- Test each adapter against recorded responses. Grow the slug list toward 100+ over time.

**Check:** Each adapter passes its fixture test; a 404 slug is skipped with a warning.

---

### Session 4: Adzuna, search and remote feeds (~3h)

- Adzuna with country=in: one query per role group (software and web, ML and AI, data and analyst, QA, intern and apprentice). Check the current free-tier limits first.
- Add one remote feed. For Remotive: at most 4 fetches a day, link back and credit it in the digest. Jooble is optional, after checking its terms.
- Wrap every source in try/except; record success, count and error in source_runs.

**Check:** Three or more sources return jobs; killing one source's network still yields results from the rest.

---

### Session 5: Email alerts source (~3h)

- EmailAlertSource reads the alerts mailbox (A) over IMAP with an app password. Fetch only from the alert senders you list.
- Parse job links and titles per sender, using saved sample emails as test fixtures. Treat email content as untrusted.
- Record processed Message-IDs in the database. Never delete or move mail. The digest goes to mailbox B, never back into A.

**Check:** Parser tests pass on the saved samples; mail from unknown senders is ignored.

---

### Session 6: Normalization (~3h)

- Job model: title, company, location, canonical_url, description_text, posted_at, source, skills[], min_years, is_intern, is_apprentice, salary_lpa or stipend, batch_years.
- Strip HTML, clean locations (Gurgaon, Calcutta, Delhi NCR), canonicalize URLs, parse dates.
- Skill extraction with word-boundary regex from your profile skills plus about 150 keywords. Beware 'C', 'Go' and bare words like 'rest'.
- Parse salary per month or per year to LPA (conversion is an estimate); detect fresher, intern, apprentice and any named batch year.

**Check:** 15 sample descriptions pass, including the 'C' and 'Go' traps and four salary formats.

---

### Session 7: Dedup + freshness (~2-3h)

- fingerprint = sha256(company | title | location), all normalized; canonical_url also unique.
- 'New' means the fingerprint is not in seen_jobs. Fresh means posted in the last 48 hours, or date unknown but first seen today.
- Upsert into jobs and seen_jobs.

**Check:** The same job arriving from two sources counts once.

---

### Session 8: Eligibility + match score (~3h)

- Hard filters: whole-word exclude titles, blocklist, required years above 2, a named batch year other than 2027, full-time salary below 3.5 LPA when listed.
- Score 0 to 10 with weights from config: skills 4, role 3, level 2, location 1 (1.0 preferred city, 0.5 elsewhere in India or remote, 0 abroad).
- Return matched skills, missing skills (tracked gaps shown but not scored), the location reason and short reasons.

**Check:** Senior roles and a 2025-batch-only listing are excluded; a fresher Python role in Pune ranks high.

---

### Session 9: Digest builder (~2-3h)

- Jinja2 HTML and plain-text templates. Two sections: internships and apprenticeships, then full-time. Each has Strong (7+) and Maybe (4 to 6).
- Each item: apply link first, then title, company, location, salary or 'salary not listed', score, matched and missing skills, source. Up to 40 items.
- Header with counts (N new, M already seen), Remotive credit, a note naming any failed source. Save the digest in the database.

**Check:** A day with zero new jobs still renders a short 'nothing new' digest.

---

### Session 10: Delivery: Telegram and email (~3h)

- Notifier protocol with Telegram and email implementations. Channels come from the profile.
- Telegram: BotFather bot and your chat id; split messages over 4096 characters.
- Email: SMTP port 587 with STARTTLS to NOTIFICATION_EMAIL (mailbox B), HTML plus plain text.
- Record delivery per channel. Mark jobs notified after at least one channel succeeds; one failing channel never blocks the other.

**Check:** The digest arrives on both channels; with one broken, the other still delivers; sending twice repeats nothing.

---

### Session 11: Scheduler (~2-3h)

- daily-digest.yml with cron '30 2 * * *' (02:30 UTC = 08:00 IST) plus workflow_dispatch.
- Secrets: database URL, PROFILE_YAML, Adzuna, Telegram, SMTP, IMAP. Scheduled runs can start late; check GitHub's current rules on inactivity.
- APScheduler is the local alternative for testing.

**Check:** A manual run sends a digest; the scheduled run fires by itself the next morning.

---

### Session 12: Tests, tuning, reliability (~3h)

- Mocked-network pytest for every source, normalize, dedup, match, digest and notify.
- Handle zero results, rate limits, a failed source (named in the digest) and a failed channel.
- Watch 3 to 5 real mornings. Tune min score, weights, noisy aliases and the blocklist. Note which sources produce jobs you actually apply to.

**Check:** Suite is green; real digests received on both channels; you would open it each morning.

---

**Milestone 1:** the digest arrives at 8 AM on Telegram and email with no action from you.

## Phase 2: private app, single user (Sessions 13 to 17)

## Anti-slop rules for the site

- **Palette:** One accent color on a neutral background. No purple gradients.
- **Buttons:** Normal rounded rectangles, not pills everywhere.
- **Icons:** None, or one consistent set. No emoji as icons.
- **Motion:** No scroll animations, no cursor effects.
- **Numbers:** Only real ones, generated at build time from source_runs and seen_jobs, with a last-updated date. No fake counters, reviews or testimonials.
- **Hero copy:** Concrete, for example: 'Checks company job boards and Adzuna at 08:00 IST, drops duplicates, and sends matches to Telegram and email.' Not 'Supercharge your career journey.'
- **Images:** Your own screenshots and diagrams only. No generated stock photos.
- **Prose:** Write it yourself or edit heavily. Keep dashes to a minimum.
- **Branding:** No 'Made with AI' footer. A 'Source on GitHub' link is enough.

## Risks and fallbacks

| Risk | Fallback |
|---|---|
| A source changes or blocks | Sources are isolated; failed sources are named in the digest; swap adapters without touching the rest. |
| Email alert layouts change | Keep saved sample emails as tests; fix one parser at a time. |
| Scheduled run is late or paused | Use workflow_dispatch; keep repo activity; APScheduler as a local alternative. |
| Too many weak matches | Raise min score, trim noisy aliases, add to the blocklist after watching 3 to 5 mornings. |
| Salary rarely listed | Keep unlisted jobs and label them; filter only when pay is stated. |
| Alias matches ordinary words | Whole-word matching, tests for traps such as 'C', 'Go' and 'rest'. |
| Secrets leak | Secrets only in .env and repository secrets; scan history; rotate anything that leaks. |
| Free host sleeps | Accept a slow first load, or use a cheap always-on host. |
